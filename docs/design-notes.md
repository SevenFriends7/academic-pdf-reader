## 📌 未发布 双栏阅读顺序：图表块被排进了别的栏

用户原话："有时候这个段的顺序是乱的"。复现命令 `node scratch/order_probe.js 6`（STM 第 6 页）。

### 一、错成了什么样

```
旧输出： 表1数据行 → 表1图注 → 表3图注 → 4.2标题 → 正文 → 表2数据行 → 表2图注
```

而且**表1 与表3 的数据行被并成了同一段**（它们都是 `figure-label`，被排到一起后就合并了）。
正确顺序应当是"左栏从上到下、再右栏从上到下"：

```
期望：   表1数据行 → 表1图注 → 表2数据行 → 表2图注 → 左栏正文 → 表3数据行 → 表3图注 → 右栏正文
```

### 二、根因：8.6 那步"全局 top/rest 二分"有三处错（`reorderFigureBlocks`）

```js
const colTop = Math.max(...colLines.map(l => l.y));            // ★错误1：整页唯一阈值
const topBlocks = blocks.filter(b => b.bottomY > colTop - 8);  // ★错误2：块的底边 vs 正文的顶边
orderedLines = [...heads, ...flat(topBlocks), ...colLines, ...flat(restBlocks), ...feet]; // ★错误3：块不分栏
```

| # | 错误 | 真实数据（STM 第 6 页） |
|---|---|---|
| 1 | `colTop` 是**整页唯一**的阈值，而两栏正文起点常常不同 | 左栏正文从 y≈139 起（上方被两张表占满），右栏从 y≈422 起；阈值取到 710（右栏最高的一行） |
| 2 | 拿**块的底边**比**正文的顶边**：块越高底边越低 | Table 2 在左栏从 y=460 一直延伸到 y=247，底边 247 ≤ 710-8 → 被判成"在正文之下"，整块搬到正文之后 |
| 3 | 块**不区分栏**，只看底边高低 | 右栏 Table 3 底边 519 > 702？不 —— 但 Table 1 图注底边 490、Table 3 图注底边 458 都在阈值之上的集合里，于是右栏的图表被排到左栏的图表前面 |

> 这三处是同一个思路的三种表现：**用"整页的单一几何量"去决定"某一栏里的位置"**。

### 三、改法：先聚"图表单元"，再让单元回到它自己的栏里

1. **聚块**（沿用）：同 section + y 相邻（≤30pt）+ 横向重叠。
2. **聚单元**（新增一层）：块之间 y 相邻（≤120pt）且横向重叠，就算同一张图表。三条配对规矩
   都是被真实页面逼出来的：
   - **上块是图注 → 不与下块合并**。这些论文的图注一律在内容**下方**，所以图注下面是"另一张图表"。
     没有这条，STM 第 6 页 Table 2 的数据行会被并进 Table 1 的单元。
   - **下块是图注 → 合并**（图注紧跟它的数据行/图）。
   - **两块都是内容 → 中间夹着图注就不能合并**。STM 第 7 页 Figure 4 的右半在 y≈534、
     Table 5 的数据行在 y≈460，只差 74pt，中间正好是 Figure 4 的图注——夹了图注就是两张不同的图表。
     没有这条，整页的图表+表格会被并成一个巨块拖到页尾（实测踩过）。
3. **单元归栏**：含"整个横跨分栏线"的块、或块分布在分栏线两侧 → 通栏单元；否则按块中心的多数侧。
   单栏页一律算一栏（否则整页宽单元的"中心"会正好贴着分栏线左右摇摆）。
4. **摆放**：栏内单元用它的**顶边**参与该栏的 y 排序（于是"表2数据行 → 表2图注 → 左栏正文"能自然排对）；
   通栏单元仍按老规矩（整个单元都在正文之上 → 最前，否则两栏之后、脚注之前）。
   **不再有任何全局阈值。**

### 四、连带修的一处：跨栏续句不再被图表块切断

顺序修对之后，右栏顶部的图表会插在"左栏末句"和"右栏首句"之间
（该页是 `…masks each for a single` → `target object. We compare…`；第 1 页 Figure 1 同理）。
9.5 的跨栏续接只看相邻两段，于是这条句子被切成两张读不懂的残句卡片。
现在允许**跳过纯图表段落**（caption / figure-label / cross）去找续句，一遇到正文/标题/脚注就停——
相邻两段的原有行为完全不变（那才是绝大多数情况）。反例有测试钉住：中间隔着正文时绝不许跨段合并。

### 五、离线核对工具（不调 API，全部用本机存档）

| 工具 | 作用 |
|---|---|
| `scratch/order_audit.js <--json>` | 逐页输出段落序列并标记三类违规：**V1 栏序倒挂**（col2 正文之后又出现 col1 正文）、**V2 图表单元离散**、**V3 半句断裂**。`VIEWER_SRC=<另一份 viewer.js>` 可对旧版本跑 before/after |

> 现在两边都按同一套规矩（`sameFigureUnit` / `sameUnit`），并写明了为什么必须一致。

## 📌 未发布 段落内的公式渲染失败（提取不完整）

用户原话："段落内的公式提取不完整导致 latex 渲染失败"。
用**本机真实回包**复现：`node scratch/formula_audit.js`（用真实的 `visionSurgery` +
真实渲染代码 + **真 KaTeX**，0 次 API）。三种，逐条修：

| # | 现象（真实数据） | 根因 | 改法 |
|---|---|---|---|
| F1 | `{"find":"learning rate 10","latex":"learning rate $10^{-5}$"}` → 界面上是一块**红色的 KaTeX 报错** | 模型把**整句连同 `$` 定界符**写进了 latex；`katex.renderToString` 报 `Can't use function '$' in math mode`，而 `throwOnError:false` **不抛异常**，它渲染成 `class=katex-error` 的红字 | 新增 `renderVisionMathHtml`：latex 里带 `$`/`\(`/`\[` 就说明它本质是"文字夹公式"，交给 `renderTextWithMath`；纯公式才整条进数学模式 |
| F2 | AOT 第 3 页第 8 段、第 4 页第 11 段、第 5 页第 9 段（都是 `type=formula`）**没有任何 latex，公式整条不渲染** | 模型是看图判断的，它给的拆分锚点经常落在**别的段落**上：<br>· p3：`parts[0]` 在本段，"公式片"的锚点却在**紧接着的下一段**；<br>· p4：连 `parts[0]` 都不在本段——index 标成了第 7 段，两个锚点却在第 10、11 段里；<br>· p5：`parts[0]` **没有锚点**（模型认为首片从本段开始），而 `parts[1]`/`parts[2]` 的锚点在第 9/10 段。<br>旧实现只在本段里找锚点，找不到就整段放弃 → 模型给的 latex 被**静默丢掉** | 按**锚点**重新解析这段拆分真正跨越的段落：起点取含 `parts[0]` 锚点的那段，`parts[0]` 没锚点时退而用含 `parts[1]` 锚点的那段；从起点往后逐段接起来重试（最多 3 段），只接模型没单独判过 split/drop 的段，内容一字不改。搜索"已被别的拆分吸收"的段要**跳过**（continue）而不是停下（break），否则第二处拆分又白丢。锚点确实不在本段时，本段照旧出卡片，**片子等循环走到它真正所在的那一段再输出**，否则公式会跑到它前面的正文之前、阅读顺序又被搞乱 |
| F4 | 译文里出现"公式 + 悬空的 `}` + 一段重复的公式"（用户反馈："这个地方翻译我感觉乱套了"） | 替换区间按 `find.length` 取，而定位是**去掉空白后**归一化匹配的：实测中文译文里的 `Y ∈ {0, 1}` 比模型写的 find `Y ∈ { 0, 1 }` 短两个字，多吃的正好是后面那个上标的 `^{`。另外区间后面紧跟的裸上标被当成了"下一个替换条目"而不是同一符号的一部分 | 新增 `locateAnchorRange()` 返回**真实命中区间**（`locateAnchorIndex` 行为一字未变）；裸上标按语义处理——latex 里**已有** `^` 就是模型一起转写过的（吃掉区间、不动 latex），没有 `^` 才是被拆成两半（并进 latex），且必须在去重**之前**做；模型自己写了 `$...$` 的新式译文的数学区间先圈出来，命中落在里面一律跳过 |
| F3 | `(̂)`（本该是公式编号 `(2)`）、行尾的 `| Ω | ̂` → 一个**漂在字外的重音符** | 帽子规则要求"组合符前面是一个字母"，这些没有基字母的帽子谁都不匹配 | 在三条残渣规则**之后**统一清掉孤儿组合符（顺序不能提前：否则 `Y ̂ t` 里那个帽子会先被吃掉、公式就丢了） |

> 顺带明确一条**设计边界，不是 bug**：替换表只覆盖模型标注到的那几处，剩下的靠本地启发式兜底；
> 而**文本层顺序被打乱的公式**（实测 cycle 第 5 页 `Y ̂ Y ̂ t = t − α`，真实公式是 `Ŷ^{l+1}_t`）
> 本地无法还原——这种只能靠模型给 latex（F2 修的就是"模型给了却被丢掉"这条）。

修前修后（同一批真实数据；样本在修复期间随用户继续阅读涨到 17 个有视觉回包的页、173 个段落、177 条 LaTeX）：

| 指标 | 修前 | 修后 |
|---|---|---|
| F1 界面出现 `katex-error` | 2 | **0** |
| F2 公式段缺 latex | 2 | **0** |
| F3 残留裸组合符 | 3 | **0** |
| F4 译文被替换表切坏 | 2 | **0** |

> **怎么区分"公式没渲染"的三种长相**（排查时先看这个）：
> ① 界面上是 `$Y \in \{0,1\}$` 这种**带美元符的原文** → KaTeX 没加载（`renderMathSpan` 的兜底就是
> `$源码$`），去 Webview DevTools 看 `katex.min.js` 是否 404；
> ② 界面上是**排版好的公式 + 旁边吊着 `}` 或 `^{...}`** → F4 那类"替换区间取错"；
> ③ 公式卡片里**只有原文、没有公式** → F2 那类"latex 被静默丢掉"。

## 📌 未发布 AI 回答里的公式：实体、`\tag`、落单的 `$`

| # | 现象（真实数据） | 根因 | 改法 |
|---|---|---|---|
| A1 | `$N(N<M)$`、`$y > t$` → 一整块**红字报错**（`Expected 'EOF', got '&'`） | Markdown 渲染是**先 `escapeHtml`、再匹配 `$...$`**（顺序不能反，见 1.3.3 的教训），于是 `<` `>` 变成 `&lt;` `&gt;` **被当成数学源码**喂给了 KaTeX | 新增 `decodeMathEntities()`，在唯一收口处 `renderMathSpan` 里先把五类实体还原 |

### 四、兜底判据的两个教训（都踩过）

- **判据方向必须"默认是数学、像代码才排除"**。第一版写成"必须命中数学特征才算数学"，

## 📌 未发布 公式与符号专项：让"问 AI"真正聚焦公式本身

用户原话："现在你要尤其关注公式和符号，现在你要通篇做出特别的优化，包括问AI公式相关的东西，
就要聚焦公式本身。"

### 一、最要紧的一条：我们有规范公式，却从没交给模型

PDF 文本层抽出来的公式**永远是残渣**。真实例子（AOT 第 6 页式 (6)，读者实际问的那条）：

```
字符层：AttLT (X l, X l, Y) = AttID (X | W l, X | W l, X | W l, Y | D), (6)
规范式：\mathrm{AttLT}(X^l, X^l, Y) = \mathit{AttID}(X^l W^l, X^l W^l, X^l W^l, Y \mid D)
```

上标全丢了、`^l` 变成了 `l`、`|` 其实是 `\mid`。而**视觉模型早就把规范式转写好了**
（`visionLatex`，实测本机 15 片公式回包 **15/15 都带 latex**），我们只拿它画卡片，
**提问时一个字都没给模型**——模型只能照残渣猜记号，答案自然含糊、符号对不上号。

改法：`collectFocusMath(para, selectedText)` 收集规范式（整式 + 与聚焦文本相关的行内公式，去重、上限 8 条），
经 `openAiAssistantModal` → `currentAiContext.focusMath` → `postMessage` → 宿主 `streamAcademicAnswer`
→ `buildAssistantPrompt`，最终在提示词里以

```
【这条公式的规范写法（视觉模型从页面图像转写）】
```latex
V' = \mathit{AttID}(Q, K, V, Y \mid D) = …
```
```

的形式交给模型，并明示"以规范写法为准、上面的残渣不要照抄"。

### 二、公式类提问的固定顺序（不跑题到研究背景）

默认回答模板是"结论先行 + 背景 + 动机 + 例子"，模型很容易把一条公式讲成研究背景综述。
所以只要 `focusMath` 非空，就追加 `buildFormulaFocusRequirement()`：

1. 用 `$$...$$` 写出**规范形式**；
2. **逐符号表**（Markdown 表格：符号 / 读法含义 / 形状或取值范围 / 依据）；
3. 一句话说清这条式子在做什么（定义？代入？等价改写？）；
4. **代一个具体的小例子走一遍**（给小的维度，把每步数值写出来）；
5. 与相邻公式的关系；
6. 残渣与规范式不一致时明确指出。

> 关键配套：**AI 回答的 Markdown 渲染器原来不支持表格**。逐符号表恰恰是解释公式最有用、
> 模型最常用的格式（真实回答 AOT #17 整段都是 `| 符号 | 含义 |`），不支持就退化成一堆竖线——
> 读者明明要"理解公式"却看到乱码。所以这次把 GFM 表格渲染补上（表头/表体/缺格补齐/`\|` 转义），
> 并专门调样式：整表可横向滚动、表头不随滚动消失、首列等宽便于与正文符号对照。

### 三、围绕公式的其它改动（同一次专项）

| 位置 | 改动 | 为什么 |
|---|---|---|
| 公式卡片 | 新增「讲透这条公式」「复制 LaTeX」 | 前者的预填问题就是逐符号模板、并带上规范式；后者是真实需求（拿去笔记/编辑器/搜索） |
| AI 弹窗 | 显示"已附上规范 LaTeX"徽标 + **把规范式排版出来** | 读者点开弹窗看到的"聚焦原文"是残渣，得让他一眼确认"要问的是这条" |
| 快捷提问 | 新增公式专用芯片「讲透这条公式」 | 让"聚焦公式"这条能力可被发现 |
| 所有提问 | 新增「数学写法」要求：一律 `$...$`、**不要用反引号包变量或公式** | 问答侧提示词以前**一个字都没提数学**，模型全用反引号包符号（实测某篇 4 条回答 `$...$` 是 0 个） |
| 精读稿导出 | 公式段落导出 `$$...$$`、正文行内公式写成 `$...$`，残渣降级成小字备查 | 根因是 `archivePageParagraphs` 的快照**没带 `visionLatex`/`visionInline`**，导出的公式永远是错的 |
| 批注 PDF 导出 | 写出「公式（规范 LaTeX）：…」 | pdf-lib 不能排版公式，但正确可复制的源码比残渣有用得多 |

### 四、离线审计新增指标（`scratch/ai_math_audit.js`）

- **A4** 变量/公式仍显示成灰底代码块的数量 —— 修前 **500 个**（14 条回答）→ 修后 **0**。
- **A5** 页存档里公式段落带规范 LaTeX 的比例。**实测 0/11**，但这不是 bug：页存档是导出用的持久化
  快照，用户机器上的历史数据是旧代码写的（快照里根本没有这个字段），重开页面重新归档就会补上。
- **A5b** **视觉回包**里的公式片带 latex 的比例：**15/15**。这才是"提问时手里有没有规范式"的真答案，
  也正好说明"手里有、却没交给模型"是这次修掉的那个缺口。

> 教训：审计指标要**分别**指向"持久化的历史数据"与"当前能拿到的实时数据"。
> 只报 A5 的 0/11 会让人以为公式提取坏了；只报 A5b 的 15/15 又会掩盖"老档导出仍然没公式"。
> 两个都报，读者才知道该做什么（重新翻一遍页面即可刷新老档）。

> 另一个实测到的坑：**同一段可能同时存在两份译文缓存**（旧式：抄的文本层残渣；新式：模型自己写
> `$...$`）。段落里记的 `cacheKey` 指向哪一份，界面上就是哪一份——排查"这段怎么和另一页看到的不一样"
> 时先按 `cacheKey` 取，别用关键词猜。

## 📌 v1.3.8 「审稿」→「专家」：真的通读全篇，且不再限长

用户原话："审稿模式太蠢了，改成专家模式，直接让 AI 阅读全篇然后无限制输出。"

### 一、为什么原来"看不到全篇"

| 环节 | 原来 | 问题 |
|---|---|---|
| 上下文来源 | 宿主 `pageTextIndex`（**翻页时**逐页 `syncPageText` 上来的） | 只有**用户翻过的页**；没翻到的章节根本不在 |

1. **webview 现抽整篇**：专家模式下用 `pdfDoc.getPage(p).getTextContent()` 把所有页拉一遍，

   `【第 N 页】…` 的整篇文本，**缓存**只抽一次，并显示进度。

2. **上限拆掉**：专家档 → 16384（接口上限），提示词写明"不限篇幅、深度优先、不许为简短牺牲推导"。
3. **档位归一**：`reviewer` → `expert` 在 webview / 宿主写回 / translator 三处都归一，

> 设计上的取舍：**只有专家档带全文**。不是省钱，而是"短问答 + 3 万 token 全文"既慢、
> 又会让模型抓不住重点；标准/简洁档继续用"当前段 + 检索 6 段"的路子。

## 📌 v1.3.7 单字母不排版、被拆开的符号要合起来

两件都来自同一次真实反馈（"单独的 N 就按文字处理，但那个 N 也是和 Y 组成的一个符号"）：

| 现象 | 判据 | 处理 |
|---|---|---|
| `$N$`（内容只有一个字母） | 模型把散文里的变量名也包进了 `$...$` | 去掉定界符，**按普通文字显示**（KaTeX 斜体夹在中文里很扎眼） |
| `$\hat{Y}_t$^N`、视觉表公式 + `^N` | 同一个符号被拆成"公式 + 裸上标"两半 | **折进同一条公式**成 `\hat{Y}_t^{N}`；只认带 `^` 的写法，裸 " N" 不碰 |

顺带把一件事钉清楚了（省得以后又当成 bug 查）：**文本层抽出来的 `Ŷ_t^N` 常常只剩 `Y ̂ t`**
——上标 `N` 在文本层里丢失了。所以"经过 N 次迭代"里那个 `N` 从来不会被渲染成公式；
真正被渲染的 `N` 只可能来自模型自己写的 `$...$`。核对脚本 `scratch/vision/residue_check.js`
（读本机存档 + 真实渲染函数，0 次 API），它现在也是排查"这个字怎么变成公式了"的第一站。

## 📌 v1.3.6 移除「视觉重排」按钮：把"重判"换成换模型

每页默认都跑视觉判断之后，按钮就是冗余入口。但它原本还负责"这一页判歪了，重判一次"，
所以删按钮**必须同时给出替代**，否则用户遇到坏结果只能干看着：

| 旧手段 | 新手段 |
|---|---|
| 点「视觉重排」→ 忽略缓存重新问一次 | **换一个视觉模型**（`academicReader.visionModel`）→ 该页缓存自动判废，下次渲染重问 |

实现：每页视觉缓存里记下**请求时配置的模型名**（`requested`）；`isUsableVisionCache` 里一比对，
不一致就当作过期。老缓存没有这个字段时退化成比较"实际服务的模型"——
这样"升级后凭空多花钱问一遍"和"换了模型却还用旧结果"两个极端都能避免。

> 顺带一个被测试抓到的真 bug：版本判断写成了 `if (Number(entry.version) < 2) return false`。
> v1 老缓存没有 `version` 字段 → `Number(undefined)` 是 `NaN` → `NaN < 2` 为 **false** →
> **老缓存直接漏过版本检查**。改成"不满足 `>= 2` 就拒"。
> 教训：这类"反向比较 + NaN"的写法在 JS 里是个安静的坑，边界值必须由测试钉住。

## 📌 v1.3.5 移除"撤销视觉改动"：安全阀变成了脚枪

那个按钮本意是"改错了能一键回到本地分段"，但它把 `disabled` 写进该页缓存，

## 📌 v1.3.4 残渣兜底渲染：别把"漏掉"都指望模型

### 一、为什么还会有漏

原文侧的公式**永远不可能是 `$...$`**（PDF 文本层抽出来就是 `Y ̂ t` 这种残渣），老译文里抄下来的
残渣也没有 `$`。1.3.3 让新译文带 LaTeX 解决了"新内容"，但只要还有一处残渣落在没有替换表、
也没有重译的文本里，用户就会看到"漏掉"——实测第 5 页 8 段里模型只给了 2 段的表。

### 二、兜底判据（形态是规则的，可以确定性转写）

| 残渣形态 | 转写 | 依据 |
|---|---|---|
| `Y ̂ t`、`Y ̂ ̂ t` | `\hat{Y}_t`、`\hat{\hat{Y}}_t` | 组合抑扬符（U+0302/0303）出现在正文里，几乎只可能是公式残渣 |
| `Y^t`、`x^2` | `Y^{t}`、`x^{2}` | ASCII 上标（正文里的 `^` 极罕见） |
| `Y 1`、`X t` | `Y_{1}`、`X_{t}` | 学术文本里的下标写法 |

**收紧的地方**（都是实测踩出来的）：
- 裸下标只认**大写**字母开头——否则 "a 2-fold increase" 里的 "a 2" 会被当成变量；
- 后面不许紧跟 `.` / `%` / `-`——"A 2.5%"、"a 2-fold" 都不转；
- 下标只取**一个 token**，不要逗号列表——`Y ̂ 1, Y` 曾被吞成 `_{1,Y}`。

反例测试：`a 2-fold increase`、`A 2.5% higher`、`Figure 1`、`Table 2`、`Section 3`、
`et al. 2019`、`其中图 2` —— 一个都不许动。

### 三、模型优先、兜底补位

提示词要求 `inline` 覆盖该段**每一个**残渣（模型给的 LaTeX 比启发式准），
但代码不依赖它：拿不到表就走兜底。两者叠加后，老译文里含残渣的句子 **10/10 都渲染出了公式**。

> 教训（这次是我自己的测试错了）：验证缓存类修复时，判据要落在**值**上。
> `test:nonprose` 原来断言"假译文的键不存在"，但清理后 webview 会重新翻译同一段——
> 键是内容指纹，**同一个键会带着中文回来**，于是测试报"假译文还在"，
> 让我一度误判"清理没生效、用户没重启"。改成断言"值含汉字"之后一切正常。

## 📌 v1.3.3 译文直接出 LaTeX（比"替换表"更根本的一条路）

### 一、为什么之前"译文里的公式排不出来"

用户问得很直接：「直接把译文输出搞成 Obsidian 那种可以自动识别 latex 不就行了吗？」
——对，而且**渲染器早就是等价实现**（`$...$` / `$$...$$` / `\(...\)` → KaTeX，1.2.0 就有）。
真正的堵点有两个，都在我们这边：

| 堵点 | 具体 | 后果 |
|---|---|---|
| 提示词反向要求 | 六处提示词都写"公式、数学符号、变量名…**原样保留**" | 模型把 PDF 残渣 `Y ̂ t = S θ (X t)` 抄进中文，压根没有 LaTeX 可认 |
| 译文行走的是纯文本 | `.sent-zh` / `.zh-paragraph-plain` 用 `escapeHtml` 直出 | 即使模型写了 `$...$` 也不会渲染 |

### 二、改法

1. **一条共用规则**（`FORMULA_LATEX_RULE`）替掉六处各写一句：公式一律转写成 `$...$`；
2. **译文与原文走同一条渲染路径**（`renderEnTextHtml`）；
3. **闸门先剥 LaTeX 再判语言**（`stripLatexForCounting`）——这条不是可选项：
   `\mathcal`/`\hat`/`\sum` 都是拉丁字母，一段"中文 + 大公式"的译文中文占比会掉到 6%，
   不剥就会稳定误判成"疑似未翻译"（实测 `$\mathcal{L}=\frac{1}{|\Omega|}\sum_{u\in\Omega}\min(...)$ 见前文。`
   未剥时 3 汉字 / 43 字母 = 6.5% < 12% 阈值）。相似度也拿剥完的译文比，
   否则"抄一遍原文再补个 `$x$`"就能绕过闸门。

### 三、顺带的好处

- **老译文不用重译**：译文里的残渣字符串与原文相同，视觉模型的替换表同样能就地渲染；
- **导出的 Markdown 精读稿自带 `$...$`**，Obsidian / Typora 直接渲染——用户最初想要的就是这个；
- 已知代价：**导出的 PDF 附录里公式是 LaTeX 源码**（pdf-lib 排纯文本，没有数学排版能力）。
  要变好看得写一个 LaTeX→Unicode 降级转换，暂未做，但不会吞内容。

> 教训：**"渲染不出来"先别怪渲染器** —— 先问"待渲染的文本里到底有没有可识别的东西"。
> 这次是两个上游（提示词要求抄残渣、译文行没接渲染）把一条早就通的路堵住了。

## 📌 v1.3.2 行内公式：最长匹配优先

替换表里经常同时存在 `Y ̂ t` 与 `Y ̂ t − 1` 这样的长短两条（短的来自相邻段，长的来自本段）。
旧实现按列表顺序取，短的那条先命中就把更精确的长条目挤掉：`Ŷ_{t−1}` 只渲染成 `Ŷ_t`，
后面还吊着一个裸的 `− 1`——**看起来"渲染了"，其实渲染错了**。改成：先按 find 长度降序接受（不重叠），
再按位置组装。

> 顺带记一笔**行内公式渲染的边界**（这是设计，不是 bug）：
> 显示层只做"视觉模型确认过的逐字替换"。模型没给某段的替换表，那段正文里的残渣就还是残渣——
> 我们**不用本地启发式去猜哪一段是公式**，猜错会把普通文字替换成公式，比"不渲染"难发现得多。
> 独立成块的公式走另一条路：`type=formula` + `visionLatex` → 块级 KaTeX。
> 真实数据核对脚本：`scratch/vision/inline_math_on_real_page.js`（本机存档 + 真实渲染代码，0 次 API）。

## 📌 v1.3.1 实测反馈回来的三个坑

### 一、"这一段的译文就是英文原文"——错不在模型，在宿主的一条启发式

`looksNonProse()` 的判据是「**超过 60 字且通篇没有句末标点 → 图表内部标签，原样保留、
不调用翻译接口**」。它本意是省掉"坐标轴标签簇"的无用请求，但**正文被从中间切开的片段
恰好长这样**：以 `:` 或 `,` 结尾、内部一个句号都没有。

视觉手术把"正文 + 公式 + 正文"拆成三段之后，这种片段大量出现 →
整批被"跳过翻译" → 缓存里被写进**原文本身** → 卡片上中文栏显示英文。

| 判据 | 误判 |
|---|---|
| `length > 60 && 无 [.!?。！？]` | `With the cyclic reference set, we can obtain the prediction for the initial reference mask in the same manner as sequential processing:`（135 字，以冒号结尾） |

**改法**：加一条"人家在叙述"的判据——**有逗号/分号，且有 the/we/can/of 这类虚词**
（`funcWords ≥ 3` 且占比 ≥15%）。标签簇（`Extra data OL J S (%) … FPS`）既没逗号也没虚词，
标题则是大写词占多数，都不受影响。**宁可把标签误送去翻译（多一次请求），
也不能把正文误判成标签（用户直接看到"整段没翻译"）。**

### 二、判据修好了，旧缓存还在——所以要做一次定向清理

假译文是按**内容指纹**缓存的：判据修好后，同样的文本仍然会命中那条旧条目，
用户会一直看到"没翻译"，除非手动逐页重译。所以打开论文时做一次**定向清理**：

- 删的条件：值里**一个汉字都没有**、长度 > 60、且明显是英文散文（从句结构）；
  或者 alignment 的 note 明确写着"未调用翻译接口"（当年那条短路路径留下的）。
- 不动的：标题、机构、表头、图内标签簇、公式残渣——它们本来就是"原文=译文"，
  但没有从句结构，判据碰不到它们。
- 只在目标语言是中文时动手（否则会把"翻成英文"的正常结果删掉）；幂等。

### 三、合并会把"下一段的行内公式替换表"一起丢掉

图二那类"右边应该有 LaTeX 渲染却没渲染"的现象，根因是：模型把公式的替换表给在了
**被判 `merge_next` 的下一段**上，而合并时只保留了前一段的 `inline`。
（第一版修法还踩了个二次丢失：类型落地那一步又按本段的 `inline` 覆盖了一次。）
现在替换表在**合并之前**按编号挂到各段上，合并时两段的替换表合起来。

顺带把长度护栏也修准了：它本意是挡"一句散文被整句替换成公式"，但模型经常把
**一整条公式**当成一个 find 给出来——那正是该渲染的东西。现在纯公式残渣
（符号/数字占比 ≥0.35）放行到 120 字，散文型的超长 find 仍然拒绝。

### 四、手术重新编号带来的"在途回包串段"

`updateArchivedParagraph(page, paraIndex, …)` 只按编号找归档项，而手术会**重新编号**段落：
在途回包会落到"编号相同、其实是另一段"上。实测症状：某公式段拿到了隔壁小节标题的译文
（`3.3 Gradient correction` → `3.3 梯度校正`），导出精读稿里就是错的。
现在回填前核对回包自带的内容指纹，核对不上一个字都不写。

> 教训：**凡是"按编号定位段落"的地方，在手术之后都必须再核对一次内容指纹**——
> 编号在手术前后不是同一个身份。同类已修的还有批注定位（改成引文文字优先）。

## 📌 v1.3.0 视觉手术：让模型判结构，让代码动刀

### 一、补上的那块缺口

1.1.0 就接上了视觉模型，但它一直只做"类型 / 阅读顺序 / 丢弃"。
`applyVisionSegments` 的注释里写着 **「合并/拆分暂不在这里做：那要动 charMap/spans…属于另一片手术」**——
于是模型说"这两段本是一段""这一段里混了正文+公式+正文"的时候，谁也没去执行，
用户看到的仍然是公式与正文混排、跨栏半句单独成卡片。这一版把手术做完了。

### 二、协议 v2 长什么样（`translator.segmentPageWithVision`）

```
{"segments":[{"i":0,"type":"...","order":1,"group":null,"action":"keep|merge_next|split|drop",
              "why":"10 字内","latex":"仅公式", 
              "parts":[{"type":"这一片的类型","at":"这一片开头的原文文字","latex":"仅公式片"}],
              "inline":[{"find":"残渣子串 ≤20 字","latex":"可渲染的 LaTeX"}]}],
 "fixes":"一句话"}
```

- `parts` 是**每片自带类型**的拆分（旧协议只有 `splitAt: ["文字"]`，拆出来全是同一个类型，
  而"正文 / 公式 / 正文"恰恰需要三种类型）；`group` 把图内文字与图注绑在一起；
  `inline` 管正文里夹着的行内公式。
- **删掉了 `columns` 与所有坐标类字段**：`columns` 从来没有消费者、探针实测还给错（1 vs 双栏），
  坐标类字段更是与"坐标只来自文本层"这条铁律冲突。
- 缓存里带 `version`，**v1 回包判废**：它们没有 parts/group/inline，套用只会得到
  "类型改了但边界没动"——正是用户抱怨的那种状态。

### 三、代码这一侧的四条硬规矩

| 规矩 | 为什么 |
|---|---|
| **坐标只来自本地文本层** | `charMap` 逐字符记录 `{span, offset}`，切开后每片只覆盖自己的字符。所以划线高亮、点中文跳英文、导出 PDF 高亮回画全都照旧精确，一行都不用改。 |
| **锚点定位失败就跳过这一处** | 三级降级：原样 `indexOf` → 归一化（去空白 + NFD 拆重音 + 统一等价字符，让模型写的 `Ŷ` 与文本层的 `Y`+U+0302 等价）→ 滑窗 + 二元组 Dice ≥0.72。都失败就**不切**，并在状态条上如实写"某处拆分点没定位到"。绝不为了一处手术去猜一个位置。 |
| **永远在"本地原件"上重放** | `localParagraphsSnapshot` 保存本地代码切出来的那一份，每次手术都在它的克隆上重放。于是翻页回来、缩放重渲染、手动点「视觉重排」都**幂等**（旧写法是在当前结果上再改一遍，合并/拆分会越叠越多）。发给模型的也是这份原件。 |
| **搬句子必验下标** | 拆分时从原段继承句与译文，合并时把"上段末句 + 下段首句"拼成一句——每次搬完都校验 `cleanText.slice(startIdx,endIdx) === text`，对不上就改用切句器重切并标 `needsRetranslate`。这个仓库被"下标错位"坑过太多次，护栏不能省。 |

### 四、三处刻意的取舍与护栏

- **拆分继承译文，合并不做半句硬拼**。拆分时原段的句下标与文本严格对应，落在片内的句子连同译文
  一起搬过来是**精确**的（既省钱又不会错）。合并时两半的逐句译文与新切句无法保证 1:1，
  硬拼就会出现"看着对齐、其实错位"的假象——所以切点在句末才搬句子，切点在句中就把跨界的
  那两句真正拼成一句（文本与译文一起拼），拼不出来就清空译文交给队列重译。**正确性优先于省一次请求。**
- **"宁可少动，不可删错"**：图块里没有明确图注时只收拢顺序、什么都不丢；模型把一整段散文
  判成 `figure/table`（图内文字）或要给 `drop` 时，本地类型被保留（只记一笔）。
  理由是**不可逆性不对称**——正文被剔掉，用户在阅读视图里直接看不到这段内容；
  而"少剔一段"最多多翻译一次。
- **`merge_next` 不能只信模型**。第二轮探针实测：同一提示词、`temperature=0`、同一页两次跑
  结果不一致，其中一次把"本段续自上一页"错标成 `merge_next`（方向反了），
  下一段其实是大写开头的新段落。所以提示词把方向写死，**代码侧再加两道护栏**：
  下一段必须以小写字母/数字/左括号/引号开头才合并（照抄本地跨栏合并的 `looksContinuation`），
  且下一段是标题/图注/表格/元信息时不合并。本地那条保守判据之所以值得照抄，
  就是因为"误合并"会把两段正常正文粘成一段，比"漏合一次"难发现、也难恢复。

### 五、探针实测（真实 API，deepseek-flash）

## 📌 v0.2.8 四个问题的修复

### 一、图注被双栏设定劈成左右两截（已修）

**根因**：分栏判定是按**单个 span** 做的（`sw > 320` 只看这一个 span 的宽度，列归属只看这一个
span 的中心）。而 PDF 常把一条图注拆成多个窄 span：

```
"Figure 3." + "Overview of the proposed" + "framework." + "for segmentation."
   └─ 被判左栏 ┘└──────── 被判左栏 ────────┘└─ 被判右栏 ─┘└──── 被判右栏 ────┘
```

于是同一行文字被劈进左右两栏。**改成先聚"物理行"，再用整行跨度判定**，同一行的所有片段
必然进同一栏。

**过程中踩到的陷阱**（值得记下来）：第一版"按 y 聚行"是错的——真实双栏论文里
**左右两栏的文字共享同一个 y 坐标**，按 y 聚行会把左右栏并成"整页宽的一行"，
于是每行都变成"通栏"、整页正文被判成图表注并合成一个巨大段落。修正为：
聚行除了 y 相近，还要求**横向间隙 ≤25pt 且该间隙不能是那条分栏沟槽**。

同时**单双栏判定也换了判据**：不再靠"行是否横跨中线"推断，而是直接看
"分栏线两侧是否都各自存在大量完全位于一侧的正文片段"。证据不足时偏向按单栏处理——
单栏页被误判成双栏会把整页并成一个巨大段落（严重），反过来只是改成按 y 排序，通常仍正确。

### 二、中文译文直接照搬原文（已修）

**根因**：我只校验了"句数是否对得上"，**从没校验过译文到底是不是中文**。
模型把英文原样吐回来时句数完全正确，于是被当成"翻译成功"直接显示。

**改法**：新增译文质量校验——中文字符占比 <25%，或与原文相似度 >0.9（疑似照搬），
即判定不合格。不合格会**带着原因重试一次**；仍不合格则如实报错（卡片显示"翻译未通过校验"），
绝不把英文当中文译文展示。校验同时接在逐句、整段、划词三条路径上。
纯短内容（公式、编号、缩写，拉丁字母 <8 个）跳过校验，避免误报。

### 三、第二页开始翻译很慢（已修）

**根因不只是并发数**，而是**免费档 Key 的每分钟请求数（RPM）限制**：逐段翻译时一页 20 段
就是 20 次请求，必然 429，而重试退避又把每次拖慢几秒——越翻越慢。

**改法**：扩展侧新增**请求合并队列**——把 120ms 内到达的多个段落合并成**一次** API 调用
（一批 4 段），请求数直接降到 1/4。协议完全不变，仍按原样逐段回包，所以前端渲染逻辑一行没动。
批量里个别段落不合格的，再单独重试那几段（部分成功不会整批作废）。
同时把前端翻译队列的并发从 2 提到 6，让请求能更快到达以凑批。

### 四、DeepSeek 现在是可以真正替代的选项

原来 `translationService: openai-compatible` 走的是"整段一次 + 每句各一次"的 N+1 次请求，
既慢又丢上下文——切过去只会更差。现在**升级成与 Gemini 同一套流程**：
一次请求拿「整段 + 严格逐句」，同样做句数与语言校验、不合格带原因重试，
并自动处理不支持 `response_format: json_object` 的兼容接口。

切换方式：命令面板 →「配置学术翻译引擎与 API Key」→ 选「配置自定义大模型」，
端点 `https://api.deepseek.com/v1`、模型 `deepseek-chat`、填入 DeepSeek Key 即可。
（该路径我**没有可用 Key 实测**，逻辑与校验已就位；若你有 Key 我可以跑一遍端到端验证。）

### 五、文案精简（去掉不必要的 emoji 与"高大上"说法）

- `双栏学术对照` → **对照翻译**；副标题 `支持划选即译与沉浸阅读` → **划选即译**
- 主题胶囊：`☀️ 白纸 / 📜 羊皮 / 🌿 竹青 / 🌙 暗夜` → `白纸 / 羊皮 / 竹青 / 暗夜`，
  提示语也从"羊皮暖阳(经典护眼暖色)"这类改成"护眼暖色"
- 段落类型标签：`👑 论文大标题` → `论文标题`、`📝 正文` → `正文` 等 10 项
- 卡片/逐句按钮：`🎯 定位 / 🤖 问AI / ✍️ 笔记 / 📋 译文 / 📋 原文` → 去掉 emoji
  （顺带也减轻了窄栏下的宽度压力）
- 右键菜单、批注气泡、筛选条、提示消息全部去 emoji；`⚙️ 翻译设置` → `翻译设置`、
  `⚡ 整页大模型精译` → `整页翻译`、`🔍 适合页面宽度` → `适合页面宽度`

## 📌 v0.2.7 自动适应窗口宽度

### 需求
左侧 PDF 自动适应窗口大小，同时**手动缩放仍然可用**。

### 实现要点
- **默认进入自动模式**：打开文档时先算出贴合比例再渲染（不会先用旧比例渲染一帧再跳变）。
- **贴合逻辑放在渲染入口**，不只挂在 resize 上 —— 这样翻到横向大图页、切换纸张主题、
  窗口变化后的重渲染都会自动贴合，不会横向溢出。
- **手动缩放优先**：点 `+`/`-`、Ctrl+滚轮、Ctrl+0 都会把自动模式关掉
  （否则用户刚放大，容器一变就被自动比例冲掉）。点顶栏「适合宽度」可重新回到自动模式，
  该按钮在自动模式下会高亮，鼠标悬停有状态说明。
- **用 `ResizeObserver` 而不是 `window.resize` 监听左栏**：拖动中间分割线并**不改变窗口尺寸**，
  但会改变左栏宽度，`window.resize` 完全收不到这个事件。
- **拖动过程用 CSS transform 给即时反馈**，停稳 220ms 后再按最终宽度重渲染
  （重渲染开销大，逐帧做会卡）。
- **可用宽度实测而非写死**：旧代码是 `pdfPane.clientWidth - 48`，实际容器左右内边距为 0，
  等于白白浪费三十多像素、页面贴不满。现在用容器的 `clientWidth`（已排除滚动条）
  减去实测内边距，再留 8px 呼吸空间。
- 比例夹在 `0.3 ~ 3.5`；可用宽度低于 120px 时放弃缩放（极端窄栏下不做无意义的强行缩放）。

### 手动缩放入口（都会自动切到手动模式）
| 操作 | 说明 |
|---|---|
| 顶栏 `+` / `-` | 每次 ±0.2 |
| `Ctrl` + 鼠标滚轮 / 触控板捏合 | 以鼠标位置为锚点缩放 |
| `Ctrl` + `+` / `-` | 每次 ±0.15 |
| `Ctrl` + `0` | 回到 100% |
| 顶栏「适合宽度」 | **恢复自动适应模式**（按钮高亮表示处于自动模式） |

## 📌 v0.2.6 界面修复说明

### 三、逐句行的「问AI / 笔记」把正文挤成细长条（已修）

**根因**：`.sent-row-actions` 是 `flex-shrink: 0` 的**常驻**子项，无论看不看得清，
都固定占掉约 **150px**（`🤖 问AI` + `✍️ 笔记` + `🎯` + 两个间距）。
侧边栏一窄，`flex: 1` 的 `.sent-content` 就只剩一百多像素，中英文双双被压成细长条。

**改法**：把这一组按钮改成**悬停浮现的浮层**——`position: absolute`（脱离文档流，
不再吃宽度）+ 默认 `opacity: 0; pointer-events: none`，在
`:hover` / `.active-sentence-row` / `:focus-within` 时才浮现。
`:focus-within` 保证纯键盘 Tab 也能唤出，不会变成"鼠标专属功能"。
浮层底色跟随行的悬停/选中底色，避免出现补丁块。

顺带把占宽的地方再收一点：行间距 12px → 10px、序号圆点 22px → 20px。
未对齐的段落现在也带上了这组按钮（浮层不占宽，所以是"白送"的）。

正文列在窄栏下大约**多出 150px**（近乎翻倍）。

### 四、卡片操作栏在窄侧边栏下溢出（已修）

**根因**：`.card-actions` 用的是 `flex-wrap: nowrap`，而 flex 子项默认 `min-width: auto`
（不会收缩到内容宽度以下）。侧边栏一拉窄，这一行就无法折行也无法压缩，最右侧按钮直接捅出
卡片边界。文件里还有**两处** `.card-actions` 规则，两处都写了同一问题。

**改法**：两处规则都改为 `flex-wrap: wrap` + `justify-content: flex-end` + `min-width: 0`，
并让 `.trans-card-header` 也可换行（窄栏时按钮组自动折到第二行、右对齐）。

## 📌 v0.2.3 修复说明（逐句翻译与 AI 问答重做）
### 一、为什么"句子提取出来之后翻译不准"——四个真实根因

| # | 根因 | 后果 |
|---|------|------|
| 1 | **模型名被静默改写**：任何含 `flash` 的模型名都被改写成 `gemini-1.5-flash` | 选中的模型被降级到已下线模型，白跑 404 后退化到劣质模型 |
| 2 | **逐句对齐靠"中文标点数量比例猜"**（旧 `alignSentencesFallback` 与 `viewer.js` 里两份重复实现） | 中文分句数 ≠ 英文句数时，同一句中文重复贴在多行，或整段译文铺满每一行 |
| 3 | **段落缓存键 = 正文前 28 个字符**（旧 `getParaSig`） | 同页两段开头相同即互相串译文（实测：某正文段落拿到了论文标题的译文） |
| 4 | **切句器把"变量名+句号"当作者缩写**（旧 `\b[A-Z]\.$` 规则） | `Let the set S. Then we define W.` 整段被吞成 1 句，逐句对齐彻底失效 |

另外：`整页翻译` 会一次性并发 30 个请求（`viewer.js`），触发 429 后整页退化为"猜对齐"。

### 二、现在改成什么样

- **一次请求拿到「整段译文 + 严格逐句译文」**：用 Gemini `responseSchema` 强约束
  `sentences` 数组长度必须等于英文句数；数量不符会带错误信息自动重试一次；仍不符才降级，
  而且**降级降得老实**——要么逐句带整段上下文单独翻（仍严格 1:1），要么只给整段译文并明确标注
  "逐句对齐未成功"，**绝不按标点猜切分伪造句对**。
- **缓存键改为全文 FNV-1a 指纹**，删除前缀模糊匹配，段落间不再串译文。
- **切句器修正下标自洽性**（`startIdx/endIdx` 与正文严格对应）并重写缩写表，去掉过激的"单字母缩写"规则。
- **扩展侧并发闸门**：整页请求压到可控并发（`academicReader.translateConcurrency`，默认 3），并对同段落请求去重。
- **去掉写死某篇论文的规则**（旧版含 `'Daily life requires'`、`'Many routine, inwardly'`），换成通用启发式。

### 三、AI 问答重做

- **删除了那段硬编码的假答案**：旧版在没有 Key 或网络失败时会返回一段编造的"学术解析"
  （内容是视频目标分割的 0.16s/frame、J&F score），还会被"存为批注笔记"写进笔记文件。
  现在所有失败都以结构化错误如实上报（未配置 Key / Key 无效 / 模型无配额 / 模型不存在 / 超时 / 被安全策略拦截）。
- **真流式**：SSE 边收边渲染，可随时点「停止」；不再有那个 15 秒就弹"备用解析"的假超时。
- **真多轮**：同一聚焦对象下保留对话历史，可连续追问，可「🧹 新话题」清空、「🔄 重答」重问。
- **全文上下文**：每解析完一页就把该页正文同步给扩展，提问时按词频检索最相关的若干段落一并送给模型；
  提示词明确要求"上下文没有的信息必须说明，严禁编造论文中不存在的内容"。
- **Markdown 渲染重写**：先转义再组装，支持标题/列表/引用/代码块/公式，`$...$` 不再被吃掉，且无 XSS。
- 模型名不再被改写；标题栏显示真实模型与"首字/总耗时"；弹窗按需拉取真实可用模型列表。

### 四、模型选择（实测结论）

同一把 API Key 上不同模型的可用性差别极大，因此改为**动态回退链**：

| 模型 | 实测结果 |
|------|----------|
| `gemini-3.6-flash` | ✅ 默认：首字约 1s，逐句对齐全部正确 |
| `gemini-3.5-flash-lite` | ✅ 极快（约 0.85s），质量略低；**不支持 `thinkingBudget: 0`**（插件会自动摘掉该参数重试） |
| `gemini-3.5-flash` | ⚠️ 可用但慢（首字 14~19s），偶发 503 |
| `gemini-3.8-flash` / `gemini-flash-latest` / `gemini-3.1-pro-preview` | ❌ 429 配额超限 |
| `gemini-2.5-flash` | ❌ 404 no longer available to new users |

建议用命令面板的 **「文献阅读：从可用模型列表中选择翻译 / AI 问答模型」** 挑选——
它会拉取该 Key 下真实可用的模型，而不是让你手打模型名。

翻译默认关闭思考（`translationThinkingBudget: 0`）：实测默认思考会多烧约 1000 token、
首字延迟从 ~1s 涨到 ~19s，而翻译并不需要推理。问答默认交给模型自己决定。

### 五、本版另外修掉的三处（来自独立代码审计）

1. **单栏论文被整页并成一个段落**：`isCrossColumn = sw > 320` 会把单栏论文的每一行都判成
   "通栏大图表注"，其 section 全为 `caption`；而 caption 分支只在遇到 "Fig. N" 时才分段 →
   整页正文并成一段（一个卡片装一页、请求超长、逐句对齐全废）。
   现在先判定页面是否单栏（正文行是否普遍"横跨页面中线"），是则关闭分栏与通栏判定。
   判据用相对阈值（`pagePdfW * 0.55`），已加回归测试确保**标准双栏论文不会被误判**。
2. **8 秒看门狗废掉并发上限**：旧版每 8 秒无条件 `activeWorkers = 0` 再放 2 路请求，
   池中旧请求仍在飞 → 同一批段落被反复重复请求（重复计费），UI 呈现"假进度"。
   现在只在"45 秒确实毫无进展"时释放 1 个槽位，绝不清零。
3. **翻页时的串段写入**：翻译在途时翻页/缩放，`currentParagraphs` 已换成新页，
   同一个 `paraIndex` 可能落到另一个段落上。现在用内容指纹核对，核对不上就不动 DOM。

## Zotero 只读联动（1.6.x）

打开论文时自动去本机 Zotero 认领这篇文献：把规范著录信息（标题/作者/年份/会议/DOI）写进导出的精读稿，把 Zotero 已索引的逐页全文加进 AI 问答上下文（问"还没翻到的页"也能答），并读取该附件下的批注。**只读，绝不改动 Zotero 库。** 这一节按"怎么复现排查"写，不只写结论。

### 一、为什么走本地 HTTP API，而不是直接读 zotero.sqlite / .zotero-ft-cache

| 方案 | 实测 / 官方说法 | 结论 |
|---|---|---|
| 直读 `zotero.sqlite` | Zotero 官方明确警告：**运行时修改数据库极易损坏库**；schema 随版本漂移（本机 61 张表）；**实测** Zotero 运行中即使 `mode=ro` 也会 `database is locked`（同目录有 `zotero.sqlite-journal`），只有 `immutable=1` 才不碰锁 | 只留给离线探针，产品不做 |
| 直读 `storage\<KEY>\.zotero-ft-cache` | 要自己定位 storage 目录、自己数 `\f` 切页；`itemAttachments.path` **实测读出 `None`**（值在 `itemData`，字段名 `path`），拿文件名还得再绕一层；拿不到 `indexedPages` / `totalPages` | 产品不做 |
| `/api/`（`http://127.0.0.1:23119`） | Zotero 自己实现的官方**只读**接口，不碰文件锁；`/items/<附件KEY>/fulltext` 的 `content` 与 `.zotero-ft-cache` **逐字节一致**（实测），并附送页数元信息 | **采用** |

怎么打开（本机 Zotero **9.0.6** 实测，四步可复现）：

1. 默认是关的：开关是 pref `extensions.zotero.httpServer.localAPI.enabled`（Zotero 源码 `defaults/preferences/zotero.js`，默认 `false`）。
2. 关着的时候探测：

   ```powershell
   (Invoke-WebRequest -Uri 'http://127.0.0.1:23119/api/' -UseBasicParsing).StatusCode
   ```

   → **403**，body 是 `Local API is not enabled`。注意：**不是**"需要 API key"（这条判断以前写错过，纠正过程见 [design-notes-zotero-source.md](design-notes-zotero-source.md) 第 2.1 节）。
3. 打开：Zotero 设置 → 高级 → 勾选「允许本机其它程序与 Zotero 通信」，**重启 Zotero**。
4. 打开之后本地读**不需要任何 key**（源码 `server_localAPI.js` 的 `_initInternal` 里没有鉴权分支）；9.0.6 **只有 GET**，写接口是 Zotero 10+ 才有 —— 所以这一版只读。

读 pref 的坑：**"prefs.js 里没有这一行" ≠ "开关关着"** —— 用户从没改过这个开关时那一行根本不存在，必须回退到 Zotero 的默认值 `false`。`readBoolPref()` 因此返回三态（`true` / `false` / `null`），把"没写"当成"开了"会直接误导用户。

### 二、三级匹配 + "认不出就不猜"

| 级别 | 判据 | 为什么需要它 | 何时放弃 |
|---|---|---|---|
| ① 完整路径 | `links.enclosure.href` 解出的路径与本地 PDF 相同 | 库里指向的就是同一个文件（例如从 Zotero 同步目录打开） | —— |
| ② 文件名 | 文件名（URL 解码 → 统一斜杠 → 转小写 → 压空白）相同 | 跨机器 / 换目录后仍然成立 | 同名多条 → 用文件大小消歧；仍不唯一 → **放弃** |
| ③ 文件大小 | `enclosure.length` 与本地字节数相同，且**库里唯一** | **真实高频场景**：用户从浏览器下载的 `2103.10088.pdf` 拖进 Zotero 被改名成 `Yang 等 - Associating….pdf`，文件名毫无关系、字节数一模一样 | 不唯一 → **放弃** |

- **全部不中 = 什么都不做**（`link: null`），而不是挑一个最像的。认错论文会把**别人的元数据、批注、全文**搬到这篇上，比不认更糟。
- 每一步都记 `matchedBy`（`path` / `basename` / `size`），日志与界面上能说清"凭什么认成了这一条"。
- 单测抓到的坑：早期版本在"文件大小"之外还要求"文件名主干相似"，结果**改名场景永远认不出来**（那条额外条件已删）。反过来，"库里有两个同字节数文件"必须放弃，不能取第一个。

### 三、页数校验为什么必须有

- Zotero 全文**按页存**，接口只给一整块 `content`，页分隔符是换页符 `\f`（实测 10 页 PDF = 10 段）。
- 宿主**不自己解析 PDF**：多一份解析器就多一处不一致。真实页数由 webview 用 pdf.js 解析后回报（`pdfOpened` 消息）。
- **触发时机**（看代码时别找错分支）：`webviewReady` 时先发一次不带页数的认领（为了尽早拿到元数据），`pdfOpened` 报出真实页数后**再发一次带 `expectedPages` 的认领** —— 页数结论以第二次为准。
- 判据：切出的段数 ≠ 真实页数（优先用 webview 报的 `expectedPages`，否则用接口的 `totalPages`）→ `pageCountMismatch = true`。
- 处理：**只发提示、不注册全文**。静默错位比没有上下文更坏 —— AI 会拿第 5 页的原文回答第 7 页的问题，用户完全看不出来。
- 复现：单测里把 `expectedPages` 传成别的值即可（`content = 'A\fB'`、`expectedPages = 10` → `mismatch = true`）。
- 顺带的收获：接口除了 `content` 还给 `indexedPages` / `totalPages`，所以"只索引了前 N 页"能被**显式说出来**，不用猜 —— 直读 `.zotero-ft-cache` 拿不到这个信息。

### 四、三个实测坑（都能在单测里复现）

| # | 坑 | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | `parseFileUrl()` 返回**小写** storage key | 拿 `nqi6n4ap` 去拼 storage 目录 / 对附件 KEY 时对不上 | 归一化（URL 解码 + 转小写）是给**比对**用的，而 storage key 是**目录名**，大小写敏感 | 归一化后的串只用来比对；key 从**原始 href** 再取一次。单测抓出 |
| 2 | 附件的**占位标题**被当成论文标题 | 界面上标题是 `PDF`，或单个字符 `T` | Zotero 导入 PDF 时附件 title 默认就是 `PDF` / `Full Text PDF` / `Snapshot`，用户手改过可能是单字符 | `isPlaceholderTitle()` + 标题回退链：父条目 `title` → 附件 `title`（非占位）→ `enclosure` 文件名（去 `.pdf`） |
| 3 | 测试桩用 `url.includes()` 做路由 | 认领在"取父条目"那一步**静默失败**（元数据全空），断言却全绿 | 子串匹配不锚定：列表端点 `/items?itemType=attachment` 与单条目端点 `/items/<key>` 共享 `/items` 前缀，单条目请求被列表路由接走 → 返回数组 → 解析失败后按"取不到"处理 | 桩改用**锚定正则**（`/api/$`、`/items\?itemType=attachment`、`/items/PAPER001$`） |

> 第 3 条是"**测试桩必须贴近真实语义**"这条老纪律的又一次应验（同类：v1.3.4 的"判据要落在值上"、双栏顺序那节的"审计工具必须与被测代码同源"）。顺带一条实测确认，写桩时别想当然：`?` 在子串匹配里只是普通字符、在正则里是量词，`/items?itemType=attachment` 两种写法都匹配不到 `/items/BBBB2222` —— 真正吞掉单条目请求的是更短的 `/items` 前缀。端点路由要么锚定全路径，要么用 `$` 收尾。

### 五、Windows：`process.exit()` 撞 libuv 断言（测试全绿却判失败）

**症状**：单测 37 条全部 ✅、失败明细为空，门禁却判失败；退出码是 **`0xC0000409`**。

**排查过程**（可照抄）：

1. 先看输出：失败明细是空的 → 不是断言失败，是**进程**出了问题。
2. 拿退出码：跑完 `node scratch/zotero/zotero_client_test.js` 之后看 `$LASTEXITCODE`（PowerShell）→ `0xC0000409`（Windows 的 `STATUS_STACK_BUFFER_OVERRUN`，Node 崩溃时的表现）。
3. 二分定位：真机联调那一段可以用环境变量跳过 ——

   ```powershell
   $env:ZOTERO_REAL_TEST='0'; node scratch/zotero/zotero_client_test.js; $LASTEXITCODE
   ```

   跳过之后退出码正常 → 变量是**那一段的输出量**，而不是网络请求本身（这个"输出量"的变量连查了三轮才定位到）。
4. 看崩溃信息：`Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)` —— libuv 在关句柄时发现句柄**正在关闭**（重复关闭）。

**根因**：`console.log` 是**异步写**（管道/文件），真机那一段输出量大，`process.exit()` 时写还没排空；而 `process.exit()` 会立刻拆掉事件循环并关句柄，与进行中的写/关闭竞争 → libuv 断言 → 进程崩溃。

**修法**：结果用 `fs.writeSync(1, ...)` **同步写**，然后**只设 `process.exitCode`**，让 Node 自己排空后自然退出（绝不再调 `process.exit()`）。

同一类坑的第二次：原生 `http` 那条兜底路径（给没有全局 `fetch` 的老 Electron 用）上挂 `AbortController`，退出时也会撞同一个 libuv 断言（Windows / Node 24）→ 改用 `http.request` 自带的 `timeout` 选项，等价且不引入信号量。

> 纪律：**"测试全绿"只说明断言过了，不说明进程正常退出。** 门禁必须同时看退出码；CI 上出现"日志里没有失败明细、退出码却非零"时，先怀疑进程崩溃，而不是去改测试。

### 六、代码位置与复现命令

### 1.6.2 补记：批注导入踩到的四个坑

1. **页高必须逐页取，不能假设"都跟第一页一样"**：`rects` 是 PDF 点坐标，翻 y 用的是**那一页**的高度；尺寸混排（扫描件 + 附录）时用统一高度会让高亮整体偏移。取不到页高就**整条丢弃** —— 翻错的高亮会画在无关段落上，用户会以为是自己标错的。
2. **颜色别用"比较 RGB 大小"猜**：Zotero 默认黄 `#ffd400` 的 R−G=0 而 G−B=212，早期启发式直接判成橙色（单测抓到）。改成官方九色盘精确匹配 + 自定义色走 HSV 色相。
3. **判重按 id，且规则是"本机那份更新"**：`zoteroData` 会到两次（先只取元数据、后带页高取批注），整批覆盖会冲掉用户在两次之间加的本机批注；用户也可能改过导入批注的颜色/笔记。所以 id 已存在就整条跳过。
4. **别触发本机的"自动修复"分支**：`renderPageAnnotations` 对"缺 rects"的批注会按段落去猜位置 —— 那是给用户手划批注准备的。导入时没有有效矩形的批注一律不进数组，而不是塞个空 rects 让它去猜。

## 事故记录：PDF 换文件夹后批注"全部消失"（2026-10-05，1.6.11 修复）

### 症状

用户把三篇论文从 `D:\kx\上海交大\梯度校正测验\梯度校正测验\` 挪到 `…\梯度校正测验\文献\`，
再打开插件时**批注全部为空**（STM 36 条、AOT 26 条、cycle 27 条）。

### 根因

`src/notesStorage.ts` 的存储键是**PDF 绝对路径的 MD5**：

```ts
const hash = crypto.createHash('md5').update(pdfUri.fsPath).digest('hex');
return path.join(this.storageDir, `paper_${hash}.json`);
```

改目录 ⇒ 路径变 ⇒ MD5 变 ⇒ 插件当成一篇全新论文 ⇒ 读到空数据。
**数据一条没丢**，全在旧键文件里；但界面上就是"消失了"。

这个设计当初是为了"同名的不同论文不会互相覆盖"，代价是**文件一移动就失联**，
而且失联方式是**静默的**——用户只会看到批注没了。

### 处置

1. **立刻恢复**（`scratch/recover_annotations.js`）：按"文件名"分组 + 用现存文件的字节数做校验，
   把旧键的批注/译文/AI 答疑并回当前键。会先备份、旧文件原样保留、按 id 去重（可重复执行）。
2. **跨 IDE 合并**：三个 IDE 的 `globalStorage` 是**各自独立**的。实测 Antigravity IDE 的存储里
   STM 还有 **4 条 VS Code 里没有的批注**（旧目录已删，属真·独有），
   用 `--merge-from=<另一个 IDE 的存储目录>` 按**同一把键**并了进来（键是路径 MD5，同键即同一篇）。
3. **永久修复**：新增身份索引 `_paper_index.json`（文件名 + 字节数 → 存储键）。
   当前路径没有存档时，按身份找回并**自动认领**；同名但字节数不同的文件**绝不匹配**。
   索引丢了也能扫历史存档重建。键的算法**故意保持不变**（换算法只会让老数据再"消失"一次）。

### 教训

- **任何"用路径/位置当主键"的持久化都会在用户整理文件时炸**。稳定身份应该是
  "文件名 + 字节数"（或内容哈希），路径只当"当前位置"。
- 数据失联必须是**可见的**：这次是静默读到空数据，用户只能自己发现"批注没了"。
- 三个 IDE 各存一份 globalStorage，**排查数据问题必须都看**，否则会漏掉只存在于另一个 IDE 的内容。
