# 本地公式模型：接进来做什么、不做什么

> 版本：1.6.20 起
> 相关代码：`src/formulaModel.ts`（宿主）、`py/formula_sidecar.py`（识别）、
> `media/viewer.js`（裁框 + 校验 + 回填）
> 实测依据：`../formula_model_probe/FINDINGS.md`、`out_manual/cases.json`

## 1. 问题被拆成三层，只有第三层需要模型

用户原话是"行内符号、公式和行间公式抓取不准"。这句话里其实是三件不同的事：

| 症状 | 真正的成因 | 该由谁解决 |
|---|---|---|
| 行内符号混进正文、残渣糊成一团 | 旧实现把一行里所有 span 用空格拼成 `cleanText`，字体边界丢了 | 文本层（已由 math layer 解决） |
| 行间公式被切成两半 / 吞进邻行 | "哪些字形属于同一条式子"这件事，几何规则表达不了 | **框**（见第 4 节） |
| `√` 被开方数是空的、分式拍平、上标丢失 | 逐字符查表**不可能**知道结构（根号管到哪、分子分母是谁） | **识别模型**（本节） |

前两层不用模型也能做，而且做得比模型准——因为 PDF 有文本层，字体名和坐标是确定的。
第三层是模型唯一不可替代的地方，也是这次改动的全部范围。

## 2. 实测给出的两条硬结论

拿真实论文（AOT.pdf 第 4、5 页）跑 PP-FormulaNet_plus-S，7 个案例：

- **框裁对的 4 次，全对。** 包括 `\frac{QK^{tr}}{\sqrt{C}}` 这种本地逐字符拼装
  永远拼不出来的结构（界面上原本是 `softmax(√)`，根号下面是空的）。
- **框裁错的 3 次，全错——而且不是拒绝，是编造。**
  模型会把邻行正文塞进 `\begin{array}` 里，输出一条"能渲染、但不是这条公式"的式子。

所以这个功能的定位被刻意压得很窄：

> **模型只吃"已经裁好的那一小块图"，不参与找框。**

谁给框？前端。`para.segments` 里 `kind === 'math'` 的那一片，自带落在哪个 span 上、
占 span 内哪一段字符——这是 PDF 文本层免费给的确定性信息，比任何检测器都准。

## 3. 字符守恒校验：这个功能能不能用，全看这一道

模型会编造，所以**每一条结果都必须被验伪**。判据不是"看起来像不像"，而是可计算的：

### 3.1 字符多重集

把 LaTeX 反解成"肉眼可见的字符"（`\frac` 不产生字符、`\alpha` 产生 α、
`\mathbb{R}` 产生 R、`\begin{array}{l}` 的 `{l}` 是列格式不是字母），
和框内文本层做**多重集**比对（不保序——分式的字符顺序本来就会变）。

两个指标：

- `coverage` = 原文里有多少字符在 LaTeX 中出现了
- `extra` = LaTeX 里有多少字符原文没有（吞邻行会把它顶上去）

判定：`coverage ≥ 0.70` 且 `extra ≤ 0.30`；原文 ≤3 字符时要求**完全相同**。

### 3.2 结构自检（光靠字符不够）

实测抓到两类"字符对得上但结果不能用"的：

- **写坏的结构**：模型把 `\begin{aligned}{` 写成 `Abegint}{`，cov=0.98 照样通过，
  但 KaTeX 渲染不出来 → 查花括号平衡、`\begin`/`\end` 配对。
- **忠实地转写了正文**：框偏大时，模型会把框里所有东西都转写，
  包括 `\mathrm{probability}` `\mathrm{logits}`，cov 能到 0.97。
  这类最危险，看起来完全像模像样 → 查 `\text/\mathrm/\operatorname` 里有没有
  非算子名的长英文词（`softmax`/`argmax`/`det` 等在白名单里）。

### 3.3 阈值是实测标定的

拿手工框那 6 个案例（`out_manual/cases.json`）跑：

| 案例 | 结果 | cov | extra |
|---|---|---|---|
| 整条 Attention 式子（框对） | **采纳** | 0.97 | 0.00 |
| 同一条但模型把 `\begin` 写坏 | 拒绝 unbalanced-brace | — | — |
| `V′∈R^{HW×C}`（框吃进正文 `AttID( re`） | 拒绝（原为采纳，extra 0.37） | 0.89 | 0.37 |
| `Y∈{0,1}^{T×H×W×N}`（框吃进正文） | 拒绝 prose-in-math | — | — |
| `Y′∈[0,1]^{HW×N}`（框吃进正文） | 拒绝 unbalanced-brace | — | — |
| 同一处但按字形紧裁 | 拒绝 unbalanced-brace | — | — |

> 早期 `extra` 门槛是 0.60，上面第 3 行就是那时漏进来的。
> 收紧到 0.30 之后，6 条里只采纳了唯一正确的那一条。

**"只采纳 1/6"不是效果差，是设计意图**：拒绝时前端保持原样（行间显示裁图、行内保留本地
LaTeX），用户最多回到改动前的状态；而错误采纳会让精读稿里出现一条内容不对、却能渲染的公式，
比原来的残渣更坏。

## 4. 为什么先不引入公式检测器（MFD）

`PDF-Extract-Kit` 的 `formula_detection`（YOLOv8）能给出行内 + 行间的框，理论上更通用。
这台机器上暂不引入，有三个具体理由：

1. **数字版 PDF 里文本层更准**：MFD 输出的是像素级框，而文本层直接告诉你
   "这 7 个 span 是 CMMI10 数学字体、基线相同"。后者不需要置信度，也不会漏。
2. **MFD 救不了行内**：实测行内公式框偏 1~2pt，模型就开始编造（第 2 节）。
   MFD 在行内小目标上的定位精度不比文本层好。
3. **工程成本**：`yolo_v8_ft.pt` 349MB + ultralytics + torch。本机 torch 目前是坏的
   （`shm.dll` 加载失败），为它引入一整条依赖链不值。

**什么时候才需要**：扫描件、公式是纯图片、ToUnicode 坏掉的 PDF——这些情况下字体信号
完全失效，文本层给不出框。那时 MFD 是唯一出路，接入点仍然是同一个 sidecar
（加一个 `detect` 命令即可，协议不用改）。

## 5. 接入后数据怎么流

```
renderPage 解析段落
  └─ para.segments（kind:'math'，带 span + 字符区间）
       ├─ 行间：整段 spans 的并集 → 3× 裁图 → 卡片显示（已有的裁图链路）
       └─ 行内 + 行间：同一张裁图 → base64 → 宿主 → sidecar → LaTeX
                                          ↓
                                   字符守恒 + 结构自检
                                          ↓ 通过
                        para.modelLatex / seg.modelLatex
                                          ↓
              ┌───────────────┬───────────┬──────────────────┐
           精读稿导出      问 AI      公式索引        行内 KaTeX 就地替换
```

几个刻意的取舍：

- **行间卡片仍然显示裁图**，不换成 KaTeX。裁图是"取样"，错误率结构性为 0；
  KaTeX 有模型误差。模型结果的价值在**文本形式**（导出、检索、喂给 AI）。
- **行内公式会就地换 KaTeX 内容**——那里本来就没有裁图兜底，残渣是可见的痛点。
- **归档即缓存**：结果写进 `pageArchive` 的 `modelLatex` / `modelInline`，
  翻走再翻回来不重复识别；`mergeArchivedParagraphs` 里「非空不覆盖」，
  避免重新解析段落时把算好的结果冲掉。
- **优先级**：`modelLatex` > `visionLatex`（云端整页视觉模型）。
  前者有硬校验，后者没有。

## 6. 已知边界

- **只在"框对 + 原文完整"时可信**。行内公式按字符比例切 span（PDF 文本层没有字符级 x 坐标），
  一个 span 里夹正文时会有 ±1 字符误差——校验会把它拦下来，表现为"这条没换上"，
  而不会换上一条错的。
- **公式很密的一页会慢**。plus-S 约 400ms/条，每页上限 40 条（长的、行间的优先），
  最坏 16 秒在后台跑完。首条永远慢（模型加载 12 秒），所以默认允许后台预取。
- **依赖用户环境**。没有 Python + paddleocr 就用不了（开关默认关，不影响其他功能）。
- **`extra` 门槛偏严**。若某类论文（大量 `\text{}` 点缀）被系统性误杀，
  调 `media/viewer.js` 里 `verifyLatexAgainstText` 的 0.30——但改之前先看 e2e 表，
  确认被拒的确实不是编造。
